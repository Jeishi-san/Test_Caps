### **3.1.6 INPUT STAGE**

The Input Stage operates across Layers 1 and 2 and encompasses account authentication, document selection, carrier preparation, and encode request submission. Users authenticate through Sanctum-protected sessions, after which Layer 2 applies policy and ownership validation prior to any steganographic processing. During encode preparation, StegoLock supports both validated carrier-pool selection and direct carrier upload, with preflight checks that compute required payload size using exact byte precision and harmonized capacity logic across the frontend, backend, and Python runtime. A safety margin is enforced before queue dispatch to reduce threshold-related failures; once accepted, the encode request is submitted to the Laravel Queue with lifecycle tracking so clients can monitor pending, processing, completed/ready, or failed states.

### **3.1.7.1 PHASE ONE: MASTER KEY AND DOCUMENT KEY DERIVATION**

Phase One establishes the cryptographic material according to the document’s configured encryption mode. Under legacy-derived mode, the system derives the Document Encryption Key (DEK) from the authenticated session Master Key and a per-document salt. Under envelope-wrapped mode, the system generates a cryptographically random 256-bit DEK and then secures access by wrapping that DEK separately for each authorized user using the corresponding Master Key context. This dual-mode mechanism preserves backward compatibility for existing records while enabling secure multi-user sharing for newly created documents.

### **3.1.7.2 PHASE TWO: ENCRYPTION**

In Phase Two, CryptoService compresses the document payload and encrypts it using AES-256-GCM, producing ciphertext and an authentication tag for integrity and tamper verification during retrieval. The resulting metadata includes the initialization vector (IV), authentication tag, integrity hash, and mode-specific key references required for subsequent decryption. Error handling is standardized to prevent disclosure of sensitive internal details while preserving operationally useful failure reporting for the processing pipeline and user interface. Sensitive key material is retained only for the active execution scope and is cleared from working memory after use.

### **3.1.7.3 PHASE THREE: SEGMENTATION**

SegmentationService partitions encrypted payloads through byte-accurate capacity planning and greedy bin-packing selection, thereby prioritizing higher-capacity carriers and potentially reducing the total number of carriers required. Segment ordering remains deterministic to support reliable reconstruction, and segment-to-carrier mapping is explicitly persisted to prevent mismatches during embedding and decoding. Preflight and runtime checks enforce effective capacity constraints with safety headroom, ensuring that payloads accepted at the interface level remain encodable by the backend pipeline. This phase also supports reusable validated carriers from the user pool, including availability and in-use protections for concurrent job execution.

### **3.1.7.4 PHASE FOUR: STEGANOGRAPHIC EMBEDDING**

In Phase Four, StegoService embeds each encrypted segment into its assigned carrier image using least-significant-bit substitution, with quality controls enforced at both per-carrier and aggregate encode levels. Peak Signal-to-Noise Ratio (PSNR) thresholds are validated during embedding, and operations that do not satisfy configured quality limits are rejected to preserve visual imperceptibility and strengthen forensic resistance. The implementation supports the Python-based embedding path with controlled fallback behavior, while structured logging captures quality and embedding failures for traceability without disclosing sensitive payload content.

### **3.1.7.5 PHASE FIVE: FINALIZATION AND CLOUD PREPARATION**

Phase Five finalizes processing by persisting document metadata, segment metadata, quality metrics, sharing grants, and audit records, and then storing generated stego artifacts through the configured storage-disk abstraction (local or cloud). Current persistence behavior maintains ciphertext in database-backed fields for decode compatibility, while final stego carrier artifacts are stored through CloudStorageService with key-based traceability. Document lifecycle status is updated atomically as jobs progress, and completion events provide client-visible status feedback and downstream access readiness. This phase also prepares sharing records so authorized users can retrieve content under policy-governed control.

### **3.1.8 OUTPUT AND RETRIEVAL STAGE**

The Output and Retrieval Stage commences only after authorization and state validation confirm that a document is decode-eligible (ready/completed state), thereby preventing cryptographic processing on pending or failed jobs. Decoding is mode-aware: legacy-derived records follow the original derivation path, whereas envelope-wrapped records obtain the user-specific wrapped DEK from grant records and unwrap it using the requester’s authenticated Master Key context. In the sharing workflow, grant creation can automatically activate viewer access by storing wrapped key material at grant time, removing the need for a separate acceptance step while preserving revocation control through grant removal. Integrity assurance is maintained through hash verification and authenticated decryption checks, and secure delivery is enforced through authenticated download controls, access logging, and time-limited retrieval mechanisms in cloud-backed deployments. The stage further supports collaborative accountability by notifying document owners when shared decode events occur, with deduplication to prevent repeated alerts for the same viewer-document pair.
